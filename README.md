# SmartSchool

React + Vite school-management platform, ready for Supabase and Vercel.

1. Copy `.env.example` to `.env` and add your Supabase URL and anon key.
2. Run `npm install`, then `npm run dev`.
3. For a new Supabase project, run `supabase/FULL_SETUP_FRESH_PROJECT.sql` once. For an existing project, verify migrations `001` through `068` are already applied, then apply new numbered migrations `069` and later in order (the GitHub Actions workflow handles changed migrations `069+` on `master` when configured).
4. Set `SMARTSCHOOL_ALLOWED_ORIGINS` as a Supabase Edge Function secret to a comma-separated list of exact app origins (for production, include `https://smart-school-blue.vercel.app`), then deploy `register-school`, `manage-school-user`, `start-school-subscription`, `start-school-activity-payment`, `flutterwave-school-billing-webhook`, and `bootstrap-super-admin`. The public registration endpoints and Flutterwave webhook have JWT verification disabled in `supabase/config.toml`; privileged registration is protected by a one-time server secret and database claim. These functions use the service-role secret only server-side; never add that secret to frontend environment variables. Setting Vercel's Supabase URL and anon key does not deploy these functions.
5. Enable email confirmation and configure Auth redirects. Enable Google under Supabase Authentication Providers and allow `/login`, `/login/*`, and `/join-school/**` on the redirect allowlist. Google school registration is submitted as a pending request under the selected school.
6. Add the frontend environment variables in Vercel and deploy.

School registration creates a pending school and its initial administrator. The school administrator can access setup and subscription details until the platform Super Admin approves the school. Every school member registration, including Google registration, stays inactive until that school administrator approves it. Billing suspensions revoke school member access immediately while preserving the school administrator's billing page.

Migration `083_profile_photos.sql` adds profile pictures to the shared sidebar and profile settings. Users can upload an image or take one with their device camera; photos are limited to 5 MB, stored in a private bucket, and each signed-in user can access only their own storage folder. Apply migration 083 to an existing project, or use the updated `supabase/FULL_SETUP_FRESH_PROJECT.sql` for a new project.

The teacher portal is organized around assigned classes, attendance, assignments, gradebook, lesson planning, timetable, quizzes, courses, and library access. Non-teaching employees receive a separate Staff portal with access only to their own employment details, approved payslips, and leave requests. School administrators invite these employees through Portal accounts. Specialist duties such as HR, Finance, admissions, inventory, and academic leadership remain separately permissioned workspaces; specialist assignments can be granted to active teacher or staff accounts. Health, counselling, transport, and boarding remain future specialist modules.

### Pilot readiness checklist

Before inviting a pilot school:

- Use a separate pilot Supabase project and confirm its schema is current. For a fresh project, run `supabase/FULL_SETUP_FRESH_PROJECT.sql` once. For an existing project, verify migrations `001` through `068`, then apply `069` through the latest migration in order.
- Deploy the required Edge Functions and configure their secrets. Confirm registration and account approval work end to end; frontend deployment alone does not deploy the functions.
- Configure Auth email confirmation and redirect URLs. Test approval and access using separate school-admin, teacher, student, and parent accounts.
- With two test schools, run `supabase/tests/tenant-isolation.manual.sql`, then check the role-specific workflows used in the pilot. This script covers only selected records and does not replace authenticated role checks.
- Use provider test credentials for payment trials. Do not treat a payment record or Finance confirmation as a bank transfer; the app's payout form records evidence only.
- Confirm database backups and Storage file backup, and complete a restore drill before loading real school data.
- Keep notifications and other external messaging disabled until the trusted delivery adapter, provider credentials, and scheduled worker are configured.

### First Super Admin account

Super Admin is a platform-wide role, separate from a school's administrator account. Public school and portal signup cannot create it. The first account is claimed once through the guarded `/super-admin/register` setup page; after that, the database keeps registration closed, even if the account is later deleted. The `/super-admin` workspace requires signing in with that account and completing MFA.

1. Apply migration `090_one_time_super_admin_bootstrap.sql` to an existing project. A new project gets it from `FULL_SETUP_FRESH_PROJECT.sql`.
2. Generate a random one-time setup key of at least 32 bytes and set it as the Supabase Edge Function secret `SUPER_ADMIN_BOOTSTRAP_TOKEN`. Keep it out of Vercel variables, source files, and chat.
3. Deploy the `bootstrap-super-admin` Edge Function and include the production app origin in `SMARTSCHOOL_ALLOWED_ORIGINS`.
4. Open `https://<your-app-domain>/super-admin/register`, enter the setup key and first account details, then sign in. The account is marked email-confirmed because the one-time key authorizes this bootstrap.
5. Remove `SUPER_ADMIN_BOOTSTRAP_TOKEN` from Edge Function secrets after the account is created. Later visits to the setup URL show that registration is closed; sign in at `/login/super_admin` or open `/super-admin` instead.
### Automatic Supabase migrations

After the historical migrations through `068` have been applied, new numbered SQL migrations from `069` onward are applied automatically when pushed to the `master` branch. Add a GitHub Actions repository secret named `SUPABASE_DB_URL` containing the PostgreSQL connection string from the Supabase Dashboard's Connect panel. The workflow applies only changed migrations numbered `069` or higher, in order. It records each filename and checksum in a private database table, skips an unchanged migration already applied by the workflow, and fails if an applied migration file is edited. Add a new numbered migration for follow-up changes instead of editing deployed SQL. Historical migrations are deliberately excluded because their remote application status must be established first.

Changed Edge Functions under `supabase/functions/` also deploy automatically to the same Supabase project. Add GitHub repository secrets `SUPABASE_ACCESS_TOKEN` and `SUPABASE_PROJECT_ID` (the project reference) for that deployment. The workflow deploys only changed function folders and preserves the `deliver-notifications` function's JWT verification setting from `supabase/config.toml`. This follows Supabase's documented [GitHub Actions deployment](https://supabase.com/docs/guides/functions/examples/github-actions) and uses the CLI's `--use-api` option for CI.

Enable GitHub Actions and configure the needed secrets before pushing changes to `master`. Database schema and Edge Function deployments then run automatically in sequence; website hosting remains managed by Vercel.

For recurring billing, create a monthly card plan in Flutterwave for each plan and currency, save its monthly price and Flutterwave plan ID in Super Admin > Subscriptions, set the Supabase function secrets `FLW_SECRET_KEY` and `FLW_SECRET_HASH`, and configure the Flutterwave webhook URL `https://<project-ref>.supabase.co/functions/v1/flutterwave-school-billing-webhook` with charge and cancellation events. Access is suspended on the first verified failed renewal event. Flutterwave may retry a failed renewal; a later successful retry restores access. This flow uses recurring card payments; M-Pesa is not supported for recurring charges.

Activity payments use the same Flutterwave secret key and webhook. Parents choose a linked learner before checkout; free activities use an in-app registration and do not open a payment page.

## Mobile app and TypeScript

SmartSchool can be installed as a Progressive Web App. Build and preview it with `npm run build` and `npm run preview`; the production preview exposes the install prompt for student, teacher, and parent accounts. Browser storage caches only the app shell and static assets. School records and portal data remain online and are never added to the offline cache. On iOS, use Share → Add to Home Screen.

The existing React app remains the shared client for all role portals. TypeScript is enabled for incremental migration of shared modules; run `npm run typecheck` before building. Authentication, role routing, and school-brand color helpers are the first typed modules. The Capacitor dependencies remain available for a later native wrapper, but native Android/iOS projects and their notification credentials have not been generated or configured.

See `docs/security-and-product-hardening.md` for the MFA, session cleanup, onboarding checklist, outbound delivery worker, and provider setup notes. `docs/backup-and-recovery.md` contains database, Storage, and restore-drill instructions.

The HR & Payroll portal is available to school administrators and teacher accounts granted an HR role. HR administrators maintain employee and salary records, prepare payroll, and submit it for approval. Principals authorize salary changes and payroll with verified MFA. Finance officers use Finance → Salary payments to record the approved transfer and confirm settlement; the payout form records evidence and does not initiate a bank or mobile-money transfer. Non-teaching staff accounts are separate from teachers and can only view their own released payslip summaries and request leave. Migration `037_hr_payroll_core.sql` creates the school-scoped HR, salary, payroll, approval, and payment-tracking records. Principal salary and payroll approval require verified MFA; payroll approval records a hash of the submitted payroll version. Migration `038_country_and_school_payment_setup.sql` adds tenant country, general currency codes, time zones, and each school’s own bank/mobile-money payment instructions. Migration `039_operations_security_and_finance.sql` adds staff attendance, controlled expense records, manual payment reconciliation with duplicate-reference protection, inventory history, finance audit events, and RLS migration assertions. Migration `041_school_role_assignments.sql` adds multi-role school staff assignments and a shared permission catalog while preserving the primary portal roles; school administrators assign roles from Staff roles & access. Migration `042_workflow_access_and_delivery.sql` adds subject-scoped assignment and assessment access, private student assignment uploads, grade limits, specialist wellbeing access, push registration, and retrying notification delivery. Migration `043_role_access_and_admissions_hardening.sql` enforces same-school specialist assignments and tightens admissions and finance policies. Migration `044_payroll_responsibility_and_payout_controls.sql` enforces the HR → principal → Finance salary workflow at the database boundary. Bank and mobile-money transfers, SmartSchool subscription checkout, contract file storage, and payslip PDF generation still require provider and private-storage configuration.

Migration `087_student_classes_subject_activities.sql` captures a learner's requested class at signup, validates it during school approval, and scopes activities to teacher-assigned classes or subjects. Apply migration 087 after 086. Migrations 088 and 089 add class history, three-term year-end promotion, and past assessment questions. Apply them in order for an existing project, or use `supabase/FULL_SETUP_FRESH_PROJECT.sql` for a new project.

Active schools have public pages at `/school/<school-slug>`. Vercel serves each page with school-specific metadata and structured data, and `/sitemap.xml` lists active school pages for search crawlers; `/robots.txt` points crawlers to that sitemap. Set `PUBLIC_SITE_URL` in Vercel to the preferred public domain when using a custom domain. Search engines control crawling and when pages appear in results, so a page may not show immediately after registration. Public profiles use the school name, level, and address.

Student and parent signups select a class or level, and the school confirms the request against its learner record before activating the account. Principals and school administrators can publish activities for the school or a class; teachers are limited by their class and subject assignments. Parents choose a linked learner before checkout, while free activities use in-app registration.
