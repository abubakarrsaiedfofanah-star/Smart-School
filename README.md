# SmartSchool

React + Vite school-management platform, ready for Supabase and Vercel.

1. Copy `.env.example` to `.env` and add your Supabase URL and anon key.
2. Run `npm install`, then `npm run dev`.
3. Apply `supabase/schema.sql`, then the historical numbered SQL migrations in order (`002` through `068`) in the Supabase SQL Editor.
4. Set `SMARTSCHOOL_ALLOWED_ORIGINS` as a Supabase Edge Function secret to a comma-separated list of exact app origins (for production, include `https://smart-school-blue.vercel.app`), then deploy `register-school` and `manage-school-user` with `supabase functions deploy register-school` and `supabase functions deploy manage-school-user`. The public `register-school` endpoint has JWT verification disabled in `supabase/config.toml`; it uses the origin allowlist and database rate limit instead. These functions use the service-role secret only server-side; never add that secret to frontend environment variables. Setting Vercel's Supabase URL and anon key does not deploy these functions.
5. Enable email confirmation and configure the Auth email templates and redirect URL for your local and production app URLs. To use the Google button on every role's shared login page, enable Google under Supabase Authentication → Providers and add the app URLs (including `/login` and `/login/*`) to the Auth redirect allowlist. Google sign-in uses existing SmartSchool profiles; school and portal registration must still go through the approved registration flow.
6. Add the frontend environment variables in Vercel and deploy.

School registration creates a pending school and its initial administrator. The school administrator can only access setup and subscription details until the platform Super Admin approves the school; student, teacher, and parent portals remain unavailable until approval. After approval, each school administrator manages accounts and branding for that school's portals. Each role signs into its own portal. Subscription plan records are managed manually; payment checkout is not integrated yet.

Migration `083_profile_photos.sql` adds profile pictures to the shared sidebar and profile settings. Users can upload an image or take one with their device camera; photos are limited to 5 MB, stored in a private bucket, and each signed-in user can access only their own storage folder. Apply migration 083 to an existing project, or use the updated `supabase/FULL_SETUP_FRESH_PROJECT.sql` for a new project.

The teacher portal is organized around assigned classes, attendance, assignments, gradebook, lesson planning, timetable, quizzes, courses, and library access. Non-teaching employees receive a separate Staff portal with access only to their own employment details, approved payslips, and leave requests. School administrators invite these employees through Portal accounts. Specialist duties such as HR, Finance, admissions, inventory, and academic leadership remain separately permissioned workspaces; specialist assignments can be granted to active teacher or staff accounts. Health, counselling, transport, and boarding remain future specialist modules.

### Automatic Supabase migrations

After the historical migrations through `068` have been applied, new numbered SQL migrations from `069` onward are applied automatically when pushed to the `master` branch. Add a GitHub Actions repository secret named `SUPABASE_DB_URL` containing the PostgreSQL connection string from the Supabase Dashboard's Connect panel. The workflow applies only changed migrations numbered `069` or higher, in order. It records each filename and checksum in a private database table, skips an unchanged migration already applied by the workflow, and fails if an applied migration file is edited. Add a new numbered migration for follow-up changes instead of editing deployed SQL. Historical migrations are deliberately excluded because their remote application status must be established first.

Changed Edge Functions under `supabase/functions/` also deploy automatically to the same Supabase project. Add GitHub repository secrets `SUPABASE_ACCESS_TOKEN` and `SUPABASE_PROJECT_ID` (the project reference) for that deployment. The workflow deploys only changed function folders and preserves the `deliver-notifications` function's JWT verification setting from `supabase/config.toml`. This follows Supabase's documented [GitHub Actions deployment](https://supabase.com/docs/guides/functions/examples/github-actions) and uses the CLI's `--use-api` option for CI.

Enable GitHub Actions and configure the needed secrets before pushing changes to `master`. Database schema and Edge Function deployments then run automatically in sequence; website hosting remains managed by Vercel.

Migration `029_school_registration_rate_limit.sql` adds a service-role-only registration throttle. Apply all migrations to the Supabase project before using the updated school portals. Payment screens provide school payment instructions but do not confirm transactions.

Migration `049_payroll_separation_of_duties.sql` reserves salary changes and payroll preparation for HR, leaves approvals to principals, and limits Finance to the staff and net-pay details required to settle salaries. Migration `050_school_broadcast_admin_only.sql` reserves bulk school broadcasts for school administrators while preserving teacher-to-contact direct messages. Migration `051_assessment_resources_subject_scope.sql` scopes teacher quiz reads, question-bank and question access, grading, accommodations, and subject-resource reads/removal to current subject and class assignments. Migration `052_school_calendar_role_access.sql` reserves school-event management for school admins, principals, and deputy principals. Migration `053_school_announcement_role_access.sql` limits announcement publishing to school administrators and assigned principals. Migration `054_course_builder_subject_role_scope.sql` limits teacher course and chapter access to courses they own in subjects currently assigned to them; school administrators retain school-wide course management. Migration `055_lesson_plan_assignment_role_scope.sql` limits teachers to lesson plans for their active class and subject assignments and keeps student reads to public plans for related classes. Migration `056_non_teaching_staff_self_service_portal.sql` adds the separate staff account, school-scoped self-service payslips, hardens employee self-service policy joins, and prevents users from changing their own portal role or school assignment. Migration `057_active_account_role_enforcement.sql` disables database access for inactive profiles, blocks self-reactivation, and checks active school administrators in privileged account and subscription operations. Migration `058_inventory_read_role_scope.sql` limits asset details to school administrators, platform administrators, and staff with inventory-view access while preserving separate inventory edit permissions. Migration `059_transport_role_scope.sql` limits routes and trip logs to school transport operators and assigned drivers; drivers can only update live status/location fields. Migration `060_active_class_subject_authorization.sql` makes class/subject management check active accounts and prevents assigning inactive teachers. Migration `061_assignment_upload_path_scope.sql` prevents replacing student upload files under another assignment or after the due date. Migration `062_transport_location_integrity.sql` validates driver-updated route status and coordinates and timestamps updates on the server. Migration `063_payroll_approval_rpc_integrity.sql` prevents callers from spoofing the approval trigger flag and enforces principal-only, non-self approval through the audited RPC. Migration `064_payroll_self_approval_and_payout_controls.sql` prevents a principal or finance confirmer from authorizing their own salary or payout. Migration `065_expense_approval_and_payment_integrity.sql` separates expense entry, principal approval, and finance payment completion. Migration `067_academic_role_separation.sql` reserves timetable changes for school administrators, principals, and assigned heads of department. Teachers, students, parents, and deputy principals retain read-only timetable access. Specialist-only accounts are directed to their assigned staff workspaces instead of teacher tools.

Migration `068_staff_attendance_for_staff_accounts.sql` adds active non-teaching Staff accounts to the attendance roster while keeping attendance management limited to principals, deputy principals, and HR administrators.

Migration `078_written_assessment_papers.sql` adds a written-paper assessment mode with private, class-scoped downloads for students. Interactive MCQ assessments remain portal-only. Parents can see assignment titles and deadlines in their family dashboard but cannot enter quizzes, download assessment papers, or submit student work. Teachers can label MCQ answers with letters, numbers, Roman numerals, custom labels, or no prefix.

Migration `079_school_public_portal_registration.sql` lists active schools on the public Portals page and lets people request student, parent, teacher, HR & Payroll, or Finance accounts under a selected school. School administrators must approve requests; student and parent requests must match a learner admission number. Public registration cannot create school administrator accounts, and a unique database index enforces one school administrator per school. For a new project, run `supabase/FULL_SETUP_FRESH_PROJECT.sql` once; it now includes migration 079. If applying numbered migrations individually, apply 001-078 first, then 079. Configure the Supabase Auth email confirmation redirect allowlist to include `https://smart-school-blue.vercel.app/login` (and your local `/login` URL for development).

## Mobile app and TypeScript

SmartSchool can be installed as a Progressive Web App. Build and preview it with `npm run build` and `npm run preview`; the production preview exposes the install prompt for student, teacher, and parent accounts. Browser storage caches only the app shell and static assets. School records and portal data remain online and are never added to the offline cache. On iOS, use Share → Add to Home Screen.

The existing React app remains the shared client for all role portals. TypeScript is enabled for incremental migration of shared modules; run `npm run typecheck` before building. Authentication, role routing, and school-brand color helpers are the first typed modules. The Capacitor dependencies remain available for a later native wrapper, but native Android/iOS projects and their notification credentials have not been generated or configured.

See `docs/security-and-product-hardening.md` for the MFA, session cleanup, onboarding checklist, outbound delivery worker, and provider setup notes. `docs/backup-and-recovery.md` contains database, Storage, and restore-drill instructions.

The HR & Payroll portal is available to school administrators and teacher accounts granted an HR role. HR administrators maintain employee and salary records, prepare payroll, and submit it for approval. Principals authorize salary changes and payroll with verified MFA. Finance officers use Finance → Salary payments to record the approved transfer and confirm settlement; the payout form records evidence and does not initiate a bank or mobile-money transfer. Non-teaching staff accounts are separate from teachers and can only view their own released payslip summaries and request leave. Migration `037_hr_payroll_core.sql` creates the school-scoped HR, salary, payroll, approval, and payment-tracking records. Principal salary and payroll approval require verified MFA; payroll approval records a hash of the submitted payroll version. Migration `038_country_and_school_payment_setup.sql` adds tenant country, general currency codes, time zones, and each school’s own bank/mobile-money payment instructions. Migration `039_operations_security_and_finance.sql` adds staff attendance, controlled expense records, manual payment reconciliation with duplicate-reference protection, inventory history, finance audit events, and RLS migration assertions. Migration `041_school_role_assignments.sql` adds multi-role school staff assignments and a shared permission catalog while preserving the primary portal roles; school administrators assign roles from Staff roles & access. Migration `042_workflow_access_and_delivery.sql` adds subject-scoped assignment and assessment access, private student assignment uploads, grade limits, specialist wellbeing access, push registration, and retrying notification delivery. Migration `043_role_access_and_admissions_hardening.sql` enforces same-school specialist assignments and tightens admissions and finance policies. Migration `044_payroll_responsibility_and_payout_controls.sql` enforces the HR → principal → Finance salary workflow at the database boundary. Bank and mobile-money transfers, SmartSchool subscription checkout, contract file storage, and payslip PDF generation still require provider and private-storage configuration.
